# テストで打ち手を確かめる

A/B テストは、2 つ以上の案を同じ条件で同時に出し、どちらが良いかを実際の数字で比べる方法。よくある失敗は、結果を見てから「成功」の基準を決めること。この Skill は、基準を始める前に計画シートへ書き、判定を計算で行い、勝った案も負けた案も記録に残す。

## 前提

- 対象は、SNS の投稿・Web サイトや LP・広告のクリエイティブなど、案を出し分けて数字を取れるもの。
- 数字の取り方は次の順で決め、計画シートに書く。途中で取り方を変えない: 媒体・解析ツールの MCP ツール → 公式 API / 公式 CLI → 管理画面から出した CSV → 利用者が貼った数字。
- 判定のスクリプトには Python 3 と `pip install numpy scipy` が要る。

## 手順

1. **伸ばす数字を 1 つ決める。** 予約・来店・応募の件数など。増えても売上に結びつかない数字（総再生数など）は選ばない。取る手段が無い数字は選び直す。
2. **お客さんが離れている段階を 1 つ選ぶ。** 段階ごとに次へ進む人の割合を並べ、いちばん低いところを選ぶ。割合の計算はコードで行う。
3. **案を出し、順番を決める。** 効果の大きさ・効果が出る確かさ・やりやすさで点を付ける。始める前に、過去に勝った案と負けた案の一覧を読む（記録シート、または下の `playbook` と `list`）。同じ案を二度試さない。
4. **計画シートを書き、一度止まって人の確認を取る。** 仮説・計測する数字・悪くしてはいけない数字・成功と中止の条件・判定する日を書く。1 パターンで変えるのは 1 か所だけ。型は [references/plan-sheet.md](references/plan-sheet.md)。**確認が取れるまで先へ進まない。**
5. **公開後の実際の数字で判定する。** 案ごとの件数が計画シートで決めた数に届くまでは「まだ分からない」と返す。判定は下のスクリプトで行い、会話の中で決めない。
6. **結果を記録に残す。** 勝った案は型として一覧に入れる。負けた案も消さない。計画シートの「結果」の欄を埋める。

## 判定のスクリプト

```
# 登録（計画シートの確認が取れたあと。指標と最小件数はここで決まる）
python3 ${CLAUDE_PLUGIN_ROOT}/skills/growth-experiment/scripts/experiment_engine.py create \
  --agent <テストの単位> --hypothesis "<仮説>" --variable <変える 1 か所> \
  --variants '["A","B"]' --metric <主な数字の名前> --min-samples <案ごとに必要な件数>

# 記録（案ごとに、実際の数字を 1 件ずつ。例: 1 日ごとの値、投稿 1 本ごとの値）
python3 ${CLAUDE_PLUGIN_ROOT}/skills/growth-experiment/scripts/experiment_engine.py log \
  --agent <単位> --experiment-id <ID> --variant B --metrics '{"<主な数字の名前>": 5.1}'

# 判定
python3 ${CLAUDE_PLUGIN_ROOT}/skills/growth-experiment/scripts/experiment_engine.py score --agent <単位> --experiment-id <ID>

# 過去のテストの一覧 / 勝ちパターン一覧
python3 ${CLAUDE_PLUGIN_ROOT}/skills/growth-experiment/scripts/experiment_engine.py list --agent <単位>
python3 ${CLAUDE_PLUGIN_ROOT}/skills/growth-experiment/scripts/experiment_engine.py playbook --agent <単位>
```

- `--agent` はテストの単位（アカウント名・サイト名・チャネル名）。記録の置き場は環境変数 `GROWTH_ENGINE_DATA_DIR` で指定する（既定はカレントディレクトリの `growth-tests/`）。作業のたびに消える場所を指定しない。
- 先頭の案（A）を基準に、ほかの案との差を Mann-Whitney U 検定とブートストラップの信頼区間で調べる。既定のしきい値は「p < 0.05 かつ 伸び 15% 以上」で勝ち（環境変数 `P_WINNER` / `LIFT_WIN` で変えられる）。**しきい値を変えるなら登録の前に変え、計画シートに書く。**
- `--min-samples` を省くと案ごとに 30 件が必要になる（`HIGH_VOLUME_AGENTS` に入れた単位は 10 件）。
- 出力の読み方: `KEEP` = 勝ち / `DISCARD`・`crash` = 負け / `TRENDING`・`running`・「データが不足しています」 = まだ分からない。
- 割合を比べるテストでは、日ごと・配信ごとの割合を 1 件として記録する。合計の人数と件数しか無いときは、スクリプトを使わず、2 つの割合の差の検定（`scipy.stats` の比率の検定やカイ二乗検定）をコードで実行し、使った方法と入力の数字を報告に書く。

## 守ること

- 判定の基準は、始めたあとに変えない。件数が足りないテストを「差が無かった」と読まない。
- 測れない数字ではテストを組まない。測れていない数字は「未取得」と書き、0 で埋めない。
- 記録は作業のたびに消えない場所（共有ドライブや記録シート）に置く。前回の記録が見つからないときは「初回」と読み替えず、「見つからなかった」と書く。
- 本番のページ・アカウント・広告を勝手に変えない。公開・配信の開始・予算の変更は、利用者の確認を取ってから行う。
- 媒体やチャネルをまたいで数字を合算して判定しない（数え方が違う）。

## 出力の型

手順 4 までは計画シート。手順 5・6 は次の型で報告する。数字には意味の文を添える。

```markdown
# テストの結果: [タイトル]（判定日 YYYY-MM-DD）

## 一言でいうと
[勝ち / 負け / まだ分からない] — [意味の文。例: 予約ページを見た 100 人のうち、予約を始めた人が 4 人から 5 人に増えた]

## 数字
| 案 | 件数 | 主な数字 | A との差 | 判定 |
|---|---|---|---|---|
（取り方: [MCP / API / CSV / 貼られた数字]、期間: [  ]）

## 悪くしてはいけない数字
| 数字 | A | B | 悪化したか |
|---|---|---|---|

## 計画シートの基準との照合
- 成功の条件: [  ] → [満たした / 満たしていない]
- 件数: 必要 [  ] 件 / 実際 [  ] 件

## 次にやること（3 つまで）
```

## フォールバック先

- 同時に出し分ける手段が無い: 前後比較にする。期間・曜日・季節の影響を受けることを書き、判定は「参考」と明記する。
- 件数が判定日までに届かない: 「まだ分からない」と返す。パターンを減らす・期間を延ばす・件数の多い上の段階で先に比べる、のどれかを提案する。基準は変えない。
- numpy / scipy が入らない: スクリプトは使わない。計画シートと記録の表（案・日付・値）を作り、入るまで「まだ分からない」とする。会話の中で勝ち負けを決めない。

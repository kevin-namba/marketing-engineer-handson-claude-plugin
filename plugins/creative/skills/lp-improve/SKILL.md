# LP を改善する

直す場所を印象で決めない。人が最も減っている場所を計測の数字で 1 つ決め、そこを 1 か所だけ変えた案を作って比べる。
すでにある LP を直すときは計測から始める。今のページを調べないまま新しい LP を作り始めない。

## 最初に確定すること

- 入力: LP のファイル（または URL と案の構成）、計測の数字（ヒートマップか GA4）、流入の種類、テストの計画と結果（あれば）
- 計測の数字は、計測サービスの MCP ツール（つないである場合）→ 公式 API / 公式 CLI（利用者の認証情報で）→
  管理画面から出した CSV・画面の画像 → 利用者が貼った数字、の順で入手する。取れなかった数字は 0 で埋めず「未取得」と書く
- 案は案の ID で見分ける。計測イベントに付ける案の ID（`variant`）と同じ値を使う（landing-page-builder と同じ）
- LP・案・計測イベント・申し込み・テストのつながりは、`../landing-page-builder/SKILL.md` の「オントロジー」の図を先に読む。図をこの Skill に写さない
- 「次に何を直すか」は手順 1 から、「この改善案を試して」は手順 1 の仮説の確認から手順 2、「テストの結果が出た」「勝った案を反映して」は手順 3 から入る

## 手順

1. 直す場所を 1 つ決める。流入元とスマホ・PC の別ごとに次の 6 段階の通過率を並べ、最も人が減っている段階を選ぶ
   （目安と読み方は `references/measurement-and-patterns.md`）。
   ページを開いた → ファーストビューの下まで進んだ → ボタンまで届いた → ボタンを押した → フォームに入力し始めた → 申し込んだ
   - ファーストビューの下で減っている: 見出しとメッセージマッチ（広告の一言と食い違っていないか）
   - ボタンまで届いているのに押されていない: ボタンの文言と位置、今申し込む理由
   - フォームで減っている: フォームの項目数

   案を作る前に、テストの計画シートを書いて人の確認を取る。型と、判定の基準の決め方は growth-experiment に従う
   （この Skill に別の型や基準を持たない）。LP のテストでは、次のように埋める

   - 仮説: 何を変えると、どの段階の数字が、なぜ動くか
   - パターン: 差し替え箇所の名前と、元の文言 → 新しい文言（変えるのは 1 か所）
   - 主な数字: 最終 CV の率。件数が足りなければマイクロ CV
   - 揃える条件: 同じ期間・同じ金額・同じクリエイティブ
   - 期間と、案ごとに必要な件数: `sample_size.py` で計算する（標準ライブラリのみ。日数は 1 週間単位に切り上げられ、
     成果 50 件が下限になる）

   ```bash
   # いまの申し込み率 2% が 2.5% になる差を見分けたい。1 日の訪問は 180 件
   python3 "${CLAUDE_PLUGIN_ROOT}/skills/lp-improve/scripts/sample_size.py" \
     --baseline 2% --target 2.5% --daily-visits 180 --variants 2
   ```
2. 元の案を複製し、その 1 か所（`<!-- lp:headline -->` などのコメントで囲んだ部分）だけを書き換えた案を作る。
   計測には案の名前を送り、URL のパラメータ（`?lp=b`）で区別する。作った案は landing-page-builder の `verify_tags.py` で検証する

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/skills/landing-page-builder/scripts/make_variants.py" \
     --base lp/a --spec lp/variants.yaml --out lp --json
   ```
3. テストの結果が出たら、計画シートの基準と期間で判定する（判定の手順は growth-experiment。勝ち / 負け / 差が出なかった）。
   ほかの数字は並べて出すだけにする。どちらかの案の成果が計画シートで決めた件数に届いていなければ「まだ分からない」とし、
   期間を延ばすかマイクロ CV に切り替えるかを人に聞く
4. 判定ごとに LP を直す
   - 勝ち: 勝った案を次のテストの元の案にする
   - 負け: 元の案に戻し、仮説のどこが違っていたかを書く
   - 差が出なかった: 元の案を残し、人が減っている段階を計測の数字で確かめ直す
5. テストの記録に 1 件追加する（`lp/tests.md`。無ければ作る）
6. 次の仮説を 1 つ決める（動かす段階と、変える 1 か所を書く）。案が尽きたら参考資料の「改善の 9 つの型」に戻る

## 守ること

- 計画シートの無い（基準が事前に決まっていない）テストは判定せず、「基準なし」と記録する。途中で片方が勝っているように見えても止めない
- 結果が出たあとに分け方（端末別・曜日別など）を増やして勝ちを探さない。気づいた傾向は次の仮説に回す
- 負けた案と差が出なかった案も、勝った案と同じ項目で記録する
- 1 回に変えるのは 1 か所だけ。思いついた案をまとめて反映しない。「次は CVR が◯% 上がる」とは書かない
- 書き換えるのは案のファイルまで。公開と配信の切り替えは人が行う

## 出力の型

変えた案の HTML / 判定と根拠 / テストの記録 1 件 / 次の仮説 1 つ。
計測から入ったときは、段階ごとの通過率の表（流入元 × 端末）と、直す場所（3 つまで）。

```markdown
## [日付] [LP の URL] テスト #[番号]
- 仮説:
- 変えた 1 か所: a = 「…」／ b = 「…」
- 条件: 期間 ◯日（開始〜終了）／ 同じ金額・同じクリエイティブ
- 計画シートの基準:
- 件数: a 訪問 ◯ / 成果 ◯ ／ b 訪問 ◯ / 成果 ◯（並べて出す数字: …）
- 結果: 勝ち / 負け / 差が出なかった / 基準なし
- 分かったこと:
- 気づいた傾向（次の仮説の候補。判定には使っていない）:
```

## フォールバック先

- 計測の数字が無い: 直す場所を印象で決めない。計測タグの状態を確かめ（landing-page-builder の「計測タグを入れる・確かめる」）、送るイベントを足す案を返す。
  数字がそろうまでの間は、メッセージマッチ（広告の一言とファーストビュー）だけを確かめる
- 件数が少なすぎる: マイクロ CV で判定する。それも足りなければ、期間を延ばすか、差の大きい変更（見出し・オファー）から試す
- LP のファイルに手を入れられない（CMS など）: 変える 1 か所の文言と、設定の手順を渡し、反映は人が行う
- Python を実行できない: 案ごとに必要な件数は成果 50 件を下限として人に決めてもらい、その件数に届く日数を 1 週間単位に切り上げて期間にする。「計算は未実施」と書く
- growth-experiment（strategy の plugin）が入っていない: 計画シートの項目（仮説・主な数字・悪くしてはいけない数字・揃える条件・
  期間・案ごとに必要な件数・勝ちと負けの基準）を書いて人の確認を取り、判定は計画シートの基準との照合だけで行う

# 配信中の広告の見直し

頼まれたことで、読む節が変わる。実績の取り方と指標の計算は 3 つで共通にし、この Skill に固定する。

| 頼まれたこと | 読む節 | 広告に触るか |
|---|---|---|
| レポートを作る | 「実績を取得して指標をそろえる」→「レポートを書く」 | 触らない |
| 調整案を出す | 「実績を取得して指標をそろえる」→「調整を提案する」 | 触らない（提案まで） |
| 定期の見直しを回す（周回） | 「周回を回す」（中で上の 2 つを使う） | 運用ログに書いた提案だけを `meta-ads-playbook` の手順で実行する |

手順中の「7 日」「3 週」「20%」は既定の例で、案件ごとに決める。

## 最初に確定すること

- 媒体、広告アカウント名、期間（「先週」も日付に直す。週次のレポートは月曜から日曜の 7 日間）、比較期間
- 成果として数える行動（Meta はこちらで行動の種別を選ぶ。Google は管理画面の設定に従う）と、
  管理画面の成果と実際の予約数の差の有無
- 目標 CPA、撤退ラインの倍数、1 回に動かしてよい幅（既定は 20%）、最低消化額（`cpa-budget-plan` の表から読む）。
  目標 CPA が決まっていなければ、調整の提案では値を作らずに `cpa-budget-plan` を先に通す
- 調整を提案するときは、各広告セットの最後の大きな編集の日付。**7 日以内のものは判定せず「学習中」と書く**
- 決まっていないものがあれば、取得を始める前に**まとめて 1 回で聞く**

## 実績を取得して指標をそろえる（共通）

1. **実績を媒体ごと・日次で取得する**。読み取りのツールだけを使う。アカウントの一覧で ID とアカウント名を確かめ、
   結果が複数ページなら最後のページまで取る。取る項目は `references/data-acquisition.md`。
   調整を提案するときは、広告セット・広告ごとの実績と、現在の日予算・配信の状態も取る
2. **前の期間と突き合わせる**。キャンペーン・広告セット・広告は、名前ではなく ID で突き合わせる（名前は運用中に変わる）
3. **単位をそろえる**。金額は媒体の単位から通貨の額に直す。CTR・CPC・CPM・CVR・CPA は媒体の値を使わず、
   表示回数・クリック数・消化額・成果の件数から計算する（式と単位は `references/metrics.md`）。
   直近数日の成果は、あとから計上されて増えることがあるので「暫定」と注記する

## レポートを書く

1. **評価する**。媒体ごとに前期間比・目標比を出し、◎ ○ △ ✕ で判定する（◎ = 目標を達成し前期間より改善 /
   ○ = 目標を達成 / △ = 目標に届かないが前期間より改善 / ✕ = 目標に届かず前期間より悪化）。
   見る順番は CTR（押されるか。低ければ見せ方を疑う）→ CVR（申し込まれるか。低ければ遷移先を疑う）→ CPA
2. **書く**。数字には比べる相手を置き（「CPA 3,200 円（前月 2,700 円、目標 3,000 円）」）、
   率には分子と分母を添える（「CVR 2.1%（クリック 1,430、成果 30 件）」）。良し悪しを言い切り、
   数字がまだたまっていない週は「今週は触らずに待つ」と書く

月次では、同じ構成に 3 つを足す: 期間別の推移（週ごと）、訴求の型別の実績（広告の名前の命名規則がある場合だけ。
無ければ推測で分類せず、広告別だけにする）、広告別の順位（増額を勧める上位と、停止か改善が要る下位）。

構成は、結論（3 行。主要指標の実績と、目標比・前期間比）→ いま何が起きているか（媒体ごとの表と判定）→
なぜそうなったか（仮説）→ 次にやること（3 つまで。担当と期限、見込む効果）→ 明細（指標の明細、成果の定義、単位、取得経路、データの限界）。

```markdown
# 広告運用レポート（<案件名>）
期間: YYYY-MM-DD（月）〜 YYYY-MM-DD（日）/ 比較: その前の 7 日 / 取得日時: … / 未取得の媒体: （あれば冒頭に）

## 1. 結論
## 2. いま何が起きているか
### Meta 広告（成果 = 予約完了 / 通貨 JPY / 取得経路: …）
| キャンペーン（ID） | 消化額 | 表示回数 | クリック | CTR | 成果 | CVR | CPA | 前期間比 | 目標比 | 判定 |
### Google 広告（成果 = 管理画面の設定に従う / …）
## 3. なぜそうなったか（仮説）
## 4. 次にやること
| 何を | 担当 | 期限 | 見込む効果 |
## 5. 明細
```

## 調整を提案する

直近 7 日と、その前の 7 日の実績で判定する。

1. 消化のペースを日予算と比べる。1 日単位ではなく 7 日の合計で見る
2. 次の順に判定し、最初に当てはまったものを採る
   - 最低消化額に届かない → 判定しない
   - 撤退ラインの額（目標 CPA × 倍数）を使って成果 0 件 → 停止を提案
   - 消化が速く成果が少ない → 目標 CPA を下げる
   - 消化が遅く成果がついている → 目標 CPA を上げる
   - 目標どおり → 触らない（予算の上限で配信が抑えられているなら、増額を提案してよい）
   - 消化が遅く成果もついていない → 値は動かさず、審査の状態と計測タグの確認を提案する
3. クリック率は直近 4 週を週ごとに取得し、3 週続けて下がっている広告は差し替えを提案する
   （どの広告を・何に、1 箇所変えるかを書く）
4. 広告セットごとに 1 行の表にまとめ、提案には「見込む効果」（どの指標が、いつまでに、どこまで動くか）を添える。
   数字がたまっていない週は「今週は触らずに待つ」と言い切る

```markdown
# 週次の運用チューニング（<案件名> / <媒体> / 対象期間: YYYY-MM-DD〜MM-DD / 比較: その前の 7 日 / 取得日時 / 取得経路）

基準: 目標 CPA … 円 / 撤退ライン … 円（× …倍）/ 動かしてよい幅 …% / 最低消化額 … 円

| 広告セット | 判定 | 根拠の数字 | 提案 | 確認の要否 |
|---|---|---|---|---|
| 髪質改善_20-39歳（ID …） | 目標どおり・予算の上限で抑えられている | 7 日の消化 10,400 円、成果 4 件、CPA 2,600 円（目標 4,000 円） | 日予算を 1,500 → 1,800 円（+20%） | 確認が要る（増額） |
| カラー_全年齢（ID …） | 停止を提案 | 消化 8,300 円（撤退ライン 8,000 円）、成果 0 件、CPA — | 停止し、クリエイティブを見直す | 即時に実行できる（停止） |
| 新規_縮毛矯正（ID …） | 学習中 | 最後の大きな編集 3 日前 | 触らない | — |
```

増額と配信開始は「確認が要る」、停止と減額は「即時に実行できる」と書き分ける。
表のあとに、クリック率の推移（直近 4 週）、見込む効果、未取得の媒体・項目と理由を添える。
媒体ごとの単位と語彙は `${CLAUDE_PLUGIN_ROOT}/skills/ad-operation/references/platform-differences.md`。

## 周回を回す

次に何を変えるかを提案し、実行し、答え合わせするまでを回す定期実行（例は週 1 回）。
段階をつなぐのが**運用ログ**（提案 1 件を 1 行で持つ台帳）。次の実行からも読める場所（共有のスプレッドシートなど）に置く。
列と例、許可待ちの通知の型、登録するプロンプトの例は `references/operation-log.md`。

- **確認画面が出る環境で動かす**（Claude Code Desktop のスケジュールタスク）。人が行うのは、確認画面の許可だけ。
  パーミッションの設定は `${CLAUDE_PLUGIN_ROOT}/skills/meta-ads-playbook/references/permissions-settings.md`
- スケジュールタスクに登録するプロンプトには、案件ごとの値（運用ログの場所、対象の媒体、通知先）だけを書く

1. **運用ログと巡回の実行の記録を読む**（実績より先に読む）。判定待ちの行、見送りになった行と理由、
   巡回（`ad-patrol`）が止めた対象を確かめる。運用ログがまだ無い（初回）ときは新しく作る
2. **直近 7 日とその前の 7 日の実績を取得する**（「実績を取得して指標をそろえる」の手順）
3. **答え合わせをする**。状態が「実行済み」で結果が「判定待ち」の行のうち、実行日から 7 日以上たったものを、
   見込む効果と実績で比べ、結果と「再現できるか」を埋める。7 日未満の行は「判定待ち」のままにする
4. **提案とレポートを作る**（「調整を提案する」と「レポートを書く」の手順）。判定待ちの行がある広告セットと、
   巡回が止めた広告セットには新しい変更を提案しない。過去に外れた仮説・断られた提案と同じ内容は出さない
5. **提案を 1 件 1 行で運用ログに追記する**（状態は「提案」。変える箇所は 1 行に 1 箇所。対象は ID も書く）
6. **追記した提案を実行する**（`meta-ads-playbook` の手順）。配信開始と予算の変更は、呼ぶ前に「何を・なぜ・見込む効果」を
   通知してから呼ぶ。断られたら、その行の状態を「見送り」にして理由を書く
7. **実行した行の状態と実行日を更新し、通知する**（結論の 3 行と、実行した変更・見送った変更の一覧）

```
【周回】<案件名> YYYY-MM-DD（実績: MM-DD〜MM-DD / 未取得の媒体: なし）
■ 結論（3 行）
■ 答え合わせ（今回埋めた行）
- 9/24 実行「平日限定プラン_30-49歳 の写真の差し替え」: 見込みどおり（クリック率 0.9% → 1.3%、クリック 182 → 251）。再現できる
■ 実行した変更（対象の ID、変更前 → 変更後）
■ 見送った変更（断られた理由）
■ 許可待ち / 人が管理画面で行う変更
■ 判定待ちのため触らなかった広告セット
```

## 守ること

数字の扱い:

- 媒体をまたいで成果の件数と CPA を足さない。消化額は同じ通貨のときだけ合計する
- 成果 0 件の CPA は「—」（0 円として扱わない）。取れなかった数字は 0 で埋めず「未取得」と理由を書く。欄を消さない
- 原因は「〜と考えられる」と書き、事実と分ける。「再現できる / できない」（季節の需要など）にも分ける
- 管理画面の成果と実際の予約数がずれている案件は、その差を提案に書く
- CTR だけを引き上げる誇大な表現を勧めない

提案と実行:

- レポートと調整の提案では、広告を変更しない。次にやることには、実行する Skill（`meta-ads-playbook`）と確認の要否を添える
- 「判定しない」条件を先頭に置く（後ろに回すと、消化額の少ない広告セットで停止や増額が提案される）
- 1 回の提案で動かす幅は 20% まで。同じ広告セットを 1 週間に 2 回変えない。変えるのは 1 回に 1 箇所
- 配信開始と予算の変更は、人の確認を通す。確認画面で断られた操作を別の方法で実行しない
- 運用ログに書いていない変更を実行しない。実行していないものを「実行済み」にしない
- 運用ログの過去の行は、状態・実行日・結果・再現できるかの欄以外を書き換えない
- 周回は、提案が無い回も通知する（「今回は触らない」と理由）
- 同じ提案を続けて許可しているなら、その条件と上限をルールにして巡回（`ad-patrol`）に任せる案を通知に書く

## フォールバック先（取得できないとき）

- 認証エラー・未連携: 再連携の手順を伝え、管理画面の CSV を 1 回の依頼で頼む（文面は `references/data-acquisition.md`）。
  調整の提案に要るのは、直近 14 日と直近 4 週、日別・広告セット別と広告別の消化額・表示回数・クリック数・成果の件数、現在の日予算
- 実績が取れない媒体: 「未取得」と理由を書き、取れた媒体の分で書き切る。0 として判定しない。レポートでは欠けている媒体を冒頭に書き、
  周回ではその媒体の行を「判定待ち」のままにする。どの経路でも取れないあいだは、調整の判定を出さない
- 目標が決まっていない: レポートは目標比の列を「目標なし」とし、前期間比だけで評価する
- 前の期間のデータが無い（初回）: 前期間比を「初回のため無し」と書く
- 現在の日予算が取れない: 増額・減額は額ではなく向きだけで書く
- 最後の編集の日付が取れない: その広告セットは「学習中かどうか不明」として判定しない
- 運用ログが読めない: 提案を作らずに止まり、読めなかったことを通知する（前の周を知らないまま提案しない）
- 共有のスプレッドシートが使えない: 運用ログを作業フォルダのファイル（CSV か Markdown の表）で持つ
- 確認画面が出ない環境で周回が呼ばれた: 配信開始と予算の変更は実行せず、状態を「提案」のままにして通知する

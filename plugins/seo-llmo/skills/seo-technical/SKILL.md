# SEO のテクニカル

サイトそのものを点検して直す Skill。ページ単位の診断と、種類ごとの細部を扱う。
サイト全体の監査（`seo` の「サイト全体の SEO 監査」の節）から委譲されたときも、ここの節で進める。

節: 「ページ診断」/「変更の見張り」/「構造化データ」/「サイトマップ」/「多言語ページの点検」/
「画像の最適化」/「商品ページの点検」/「まとめて生成するページ」

## ページ診断

> **使う場面**: 1 ページを、オンページ要素・本文の質・メタタグ・構造化データ・画像・速度の順に通しで診る。
> 「このページを見て」「1 ページだけ診断して」で使う。
> ※日本語記事のリライト指示書は `seo-content` の「記事のリライト指示書」の節、CVR の観点は LP 改善の Skill（第 4 章）。

### 手順
1. このページが狙う語と、上位に並んでいる形を確かめる
2. 上から順に点検し、指摘に**直す手間の目安**を付ける（数時間 / 数日 / 1 か月以上）
3. 上位 3 つに絞って出す（全部出すと誰も動かない）

**出力**: 現状 → 指摘（重大度・手間）→ 直す順番 → 直した後の確かめ方

### 守ること
- 文字数の目安（title 30〜60 文字、meta description 120〜160 文字）は運用上の経験則で、Google の基準ではない。合否にしない
- HTML だけからは表示速度を測れない。実測は `seo-measurement` の「表示速度の計測」の節に渡す

## 変更の見張り

> **使う場面**: 主要ページの「正常な状態」を控え、次の回に差分を取って意図しない変更を見つける。
> 「改修で壊れていないか見て」「デプロイ後のチェック」「前回と比べて」で使う。

### 控える項目
タイトル / 説明文 / 正規 URL / 登録の可否の指定 / 見出し / 構造化データ /
HTTP の状態 / 表示速度の実測

### 手順
1. 前回の控えを**外の永続先**（過去の成果物・記録シート）から読み直す。
   無ければ「今回が基準。差分は次回から」と先頭に書く
2. 差分に重大度を付ける：登録拒否・正規 URL の変更・404 は即時。
   タイトルと見出しは 1 週間以内。文言の軽微な変更は記録だけ
3. 今回の状態を、次回の基準として成果物に残す

### やらないこと
- 全部の差分を同じ重さで人に読ませない（重要な 1 件が埋もれる）
- 控えが無いのに「変更なし」と書かない。変更が意図したものかは人に確かめる

## 構造化データ

> **使う場面**: ページの内容を検索エンジンが読める形で書き添える（構造化データ）。検出・検証・生成を行う。
> 「構造化データ」「JSON-LD」「リッチリザルト」「マークアップを付けて」で使う。

### 手順
1. ページの種類に合う**いちばん具体的な型**を選ぶ（汎用の型のままにしない）
2. 必須項目を埋め、推奨項目は分かるものだけ埋める
3. **ページに表示されている内容と一致させる**（表示に無い値を書かない）
4. 分からない値は推測で埋めず、「要確認」の印を残して人が埋めてから公開する

### やらないこと
- 自分で管理している口コミの評点を自社ページに書かない
- 1 つのデータに複数拠点を並べない（拠点ごとに 1 つ、識別子を分ける）
- 「入れれば順位が上がる」と書かない（直接のランキング要因ではない）

検出時の点検項目、型の選び方、装飾表示が終わった型、JSON-LD の雛形は `references/schema-markup.md` にある。

## サイトマップ

> **使う場面**: 既存のサイトマップを検証するか、業種別の雛形で新規に作る。
> 「サイトマップを作って」「サイトマップを見て」で使う。
> ※送信は外部反映なので、確認画面を通して `seo-measurement` の「検索実績の取得」の節から行う。

### 手順
1. 入っている URL を数え、**登録してほしくないページ**が入っていないか見る
   （検索結果ページ・絞り込みの結果・テストページ）
2. 正規の URL と一致しているかを確かめる（末尾のスラッシュ・パラメータ）
3. 最終更新日が全件同じ日になっていないか見る（自動生成の誤り）
4. 件数が多いときは種類ごとに分ける（1 ファイルは 50,000 URL まで、または非圧縮で 50MB まで）

**出力**: 入っている件数・種類別の内訳・除外すべき URL の一覧

### 守ること
- 入れるのは、200 を返し、noindex でなく、canonical にした絶対 URL だけ。実在しない URL を入れない
- 取得できなかった URL を「問題なし」に数えない

## 多言語ページの点検

> **使う場面**: 多言語・多地域のページの対応関係を検証し、誤りを見つけて直す。
> 「多言語の SEO」「hreflang」「英語版が出てこない」で使う。

### 誤りが起きやすい 5 点
1. 自分自身への指定が抜けている
2. 相互に指し合っていない（英→日 だけあって 日→英 が無い）
3. 言語と地域のコードが間違っている（国コードを言語コードに使っている）
4. 既定の言語の指定が無い
5. 正規 URL と食い違っている

### 手順
対応表を作り、上の 5 点を順に確かめ、直したコードを**すべての言語版のぶん**生成する。
言語の切り替えが自動転送で行われているなら、それも一緒に報告する。

対応表の形、誤りごとの直し方、コードの例は `references/hreflang-check.md` にある。

## 画像の最適化

> **使う場面**: 既存画像の代替テキスト・形式・対応サイズ・遅延読み込み・ズレ防止を点検して直す。
> 「画像を最適化して」「alt を付けて」「画像が重い」で使う。
> ※画像の新規生成は画像生成の Skill（第 4 章）。

### 手順
1. **どれを遅らせないか**を先に決める（最初に見える 1〜2 枚）
2. 残りを遅延読み込みにする
3. 幅と高さを指定し、読み込み中にレイアウトがずれないようにする
4. 代替テキストは**写っているものを説明する**（キーワードを詰めない）
5. 装飾の画像は代替テキストを空にする

**出力**: 1 行 1 画像の表（URL・サイズ・形式・代替テキストの現状と案・遅延の可否）

### 守ること
- 代替テキストは画像を見てから書く。見られないときは「要確認」と残す
- 変換していないのに「変換した」と書かない。変換のツールが無ければ指示書までを出す

## 商品ページの点検

> **使う場面**: 通販サイトの商品ページを点検する（商品の構造化データ・在庫切れ・URL の分裂・モールとの差）。
> 「EC の SEO」「商品ページを見て」「ショッピングに出てこない」で使う。

### 手順
1. 価格・在庫・通貨・返品条件が、表示と構造化データで一致しているか
2. 在庫切れのページの扱いが決まっているか（戻る見込みがあるかで分ける）
3. 同じ商品のページが何本あるかを数え、正規の URL を決める
4. モールに同じ商品がある場合、自社が上に来る理由をページ内に持たせる

### 守ること
- 価格の比較を載せるなら、取得日と取得元の URL を必ず添える
- 商品の構造化データを描画後に差し込む作りにしない

## まとめて生成するページ

> **使う場面**: データからページを大量に作るときの計画と、公開前の品質ゲートを決める。
> 「地域 × サービスのページを作りたい」「用語集を作る」「テンプレートで量産」で使う。

### 先に決める
- URL の規則と、ページ間のリンクの張り方
- **公開の条件**（機械で確かめられるものだけ）

### 品質ゲートの例
- 入れ替えテスト：地名を別の地名に入れ替えても文章が成り立つなら、公開しない
- そのページにしか無い内容（写真・人・行き方・実際の声）が 1 つ以上あるか
- 重複した本文の割合がしきい値を超えていないか

**やらないこと**: すべてを一度に公開しない（少数で出し、登録と流入を計測してから広げる）

## 共通の規則

- **最初の HTML と描画後の HTML の両方を見る。** 片方だけでは「タグは入っている」と「Google には見えていない」を区別できない
- **各所見に、根拠（URL と実測値）と取得経路を付ける**
- **分からない値を推測で埋めない。** 「要確認」の印を残し、人が埋めてから公開する
- **直すのは提案まで。** サイトの変更・サイトマップの送信は外部への反映なので、内容を見せて人の確認を取る
- **取得できなかった項目は「未取得」と書く。** 0 や「問題なし」にしない

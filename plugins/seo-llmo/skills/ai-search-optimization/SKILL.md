# AI の回答での可視性（AIO / GEO / LLMO）

AI の回答は、複数の情報源をまとめて 1 つの答えを作る。問われるのは「何位か」ではなく「答えの材料に選ばれるか」。
この Skill は、対象（AIO / GEO / LLMO）を決めてから、前提の点検・網羅の確認・言及の計測を行う。

節: 「AI の回答での可視性」（起点）/「クエリファンアウトの網羅確認」/「AI の回答での言及の定点計測」

## AI の回答での可視性

> **使う場面**: AI の回答に自社が選ばれるための診断と改善の起点の節。AIO・GEO・LLMO の
> どれを対象にするかを決めてから、前提の点検・網羅の確認・計測・改善案を返す。
> 「LLMO をやりたい」「AI 検索で出てこない」「AI Overviews に載りたい」で使う。
> ※サイト全体の技術監査は `seo` の「サイト全体の SEO 監査」の節、記事の新規作成は `seo-content` の「記事制作の全工程」の節へ。

### 0. 対象を決める（必ず最初に書く）
- AIO: Google の AI による概要・AI モード。材料は Google の検索インデックス
- GEO: 検索して答える AI 全般。エンジンごとに分けて扱う
- LLMO: 検索しない回答を含む。効果が出るまでモデルの学習を待つ

依頼文から決められなければ AIO と GEO を対象にし、その前提を冒頭に書く

### 1. 前提の点検（3 つ共通）
- robots.txt: 検索用クローラー（Googlebot / bingbot / OAI-SearchBot /
  Claude-SearchBot / PerplexityBot）を止めていないか。
  学習用（Google-Extended / GPTBot / ClaudeBot）は現状を書くだけ（事業判断）
- 本文がサーバー側で描画されているか。nosnippet・max-snippet の指定
- 構造化データが見えている本文と一致しているか。ブランド名の表記が揃っているか

### 2. 中身の点検
- 登録済みの質問ごとに、クエリファンアウトの網羅確認の節へ渡す
- 主要ページを `seo-content` の「ページ品質の点検」の節へ渡し、E-E-A-T の所見を受け取る

### 3. 計測
- 登録済みの質問だけで測る。質問の文言は変えない
- 検索が走った回答（GEO の指標）と、検索なしの回答（LLMO の知識の指標）を分けて集計する
- エンジン間で合算・比較しない

### 4. 出力
- 一言でいうと（3 行）/ 対象（AIO・GEO・LLMO）/ 前提の不備 / 網羅の不足と追記案 /
  計測結果（エンジン別）/ 次に測る日
- 施策ごとに「効果が見えるまでの目安」を書く（AIO・GEO は再クロール後、LLMO はモデルの更新後）

### しないこと
- llms.txt の設置を主な施策にしない（主要な AI 検索が使っている根拠が乏しい）
- 分かれた検索語ごとにページを量産しない
- 計測していない数値を「AI での露出」として書かない。「確実に引用される」とも書かない
- robots.txt の変更・構造化データの実装・ページの公開は外部への反映。案を見せて確認を取り、反映は人が行う

## クエリファンアウトの網羅確認

> **使う場面**: AI 検索への質問 1 本について、AI が分けて調べそうな検索語を予測し、
> サイトの各ページがそれに答える段落を持っているかを確かめる。
> 「AI にこの質問をされたとき、うちのサイトで答えられているか」「ファンアウトの網羅を見て」で使う。
> ※言及率の計測そのものは言及の定点計測の節、記事の新規作成は `seo-content` の「記事制作の全工程」の節へ。

### 入力
- 質問（計測に登録済みの文言をそのまま使う）
- 対象サイトの URL の一覧
- あれば: 計測で記録された「AI が実際に投げた検索語」と、Search Console のクエリ

### 手順
1. 質問を、料金・場所・対象者・比較・口コミ・手順・条件の切り口で分け、
   検索語を 8〜15 個予測する。各検索語に「予測」と印を付ける
2. 計測で記録された検索語があれば並べ、予測と一致したものは「実測」に改める。
   予測に無かった実測の検索語は、そのまま追加する
3. 検索語ごとに、答えになる段落がサイトにあるかを、ページを読んで判定する
   - 語句が含まれているだけでは「ある」にしない。問いに言い切りで答えている段落だけを数える
   - 段落の冒頭 2 文で答えが分かるかを見る
4. 答えが無い検索語について、追記するページと、追記する段落の案（200 字程度）を書く

### 出力
- 検索語 / 予測か実測か / 答えている段落のある URL（無ければ「なし」）/ 追記案 の表
- 「実測」の行を先に並べる（予測は外れることがある）
- 取得できなかったページは「なし」に数えず「未取得」と書く

### しないこと
- 検索語ごとに新しいページを作る提案をしない。既存のページへの追記を先に検討する
- 数値や事実を追記案に創作しない。分からない箇所は【要確認】と残す

## AI の回答での言及の定点計測

> **使う場面**: AI の回答での言及を、登録済みの質問で定点計測する。1 つの質問を 1 つのエンジンに投げた結果を
> 1 サンプルとして記録し、エンジンごとに集計する。
> 「AI の回答で自社が出るか測って」「言及率を計測して」「先月と比べて言及は増えたか」で使う。

### 手順
1. 質問の定義（ブランド語・自社ドメイン・競合・質問の一覧）を確かめる。無ければ計測せず、登録の案内を返す
2. 課金の前に、本数（質問数 × エンジン数）を利用者に見せる
3. 質問をそのままエンジンごとに投げ、1 サンプルごとに、検索が実行されたか・言及・引用・モデルが実際に投げた検索語を記録する
4. エンジンごとに集計する（言及率の分母は、検索が実行されたサンプルだけ）
5. 言及されなかった質問は、モデルが投げた検索語を並べ、クエリファンアウトの網羅確認の節へ渡す

### 守ること
- 「言及されなかった」と「検索されなかった」を分ける。成立が 0 件なら言及率は 0% ではなく「無し」
- エンジン間で足さない・比べない。アプリ名を主語にしない
- 質問の文言を変えない。変えたいときは新しい id で足す
- 測れなかったエンジンは「未計測」と理由を書く（「計測済み」と返さない）

質問の定義の形、1 サンプルの記録の項目、検索が実行されたかの判定、集計の数え方は `references/ai-mention-tracking.md` にある。

## 共通の規則

- **対象（AIO / GEO / LLMO）を最初に書く。** 効果が出るまでの時間が違うので、混ぜると「施策をしたのに変わらない」という誤った評価になる
- **「言及されなかった」と「検索されなかった」を分ける。** 言及率の分母は、検索が実行されたサンプルだけにする
- **エンジン間で足さない・比べない。** API の回答とアプリの回答が一致するとは限らない
- **質問は登録済みの文言だけを使う。1 回の結果で判断しない。** 回答は毎回同じにはならない
- **学習用クローラーの扱いは事業の判断。** 現状を書くだけにし、許可・拒否を勝手に変えない

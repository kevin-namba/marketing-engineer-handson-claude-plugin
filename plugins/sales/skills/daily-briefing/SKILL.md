# 毎朝のブリーフィング

ダッシュボードは毎日は見てもらえない。朝に届く 1 通にして、人が見に行かなくても異常だけが届く形（push 型）にする。

## 入力

| 入力 | 取り方（取れた経路を使う） | 取れないとき |
|---|---|---|
| 商談一覧（自分の開いている案件・今月成約予定・次アクションが空か期限超過・停滞） | CRM の MCP ツール → 案件表の CSV → 利用者が貼った一覧 | 数字とアラートのセクションを作らない |
| 直近の約束事 | 議事録データベース → 利用者が貼った議事録 | 「滞留しているフォロー」を作らない |
| 今日の予定 | 依頼した人が伝える → カレンダー → 次アクションと成約予定から拾う | 「今日の会議」を作らない |
| Web のシグナル（出店・受賞・採用） | Web 検索（任意） | 省く |

## 手順

1. **入力を読む。** CRM を参照できないときは、今日の予定・注力している案件・緊急事項の 3 つを 1 回で聞く。
   停滞は、週次レビューのスクリプトと閾値で判定する（判定を 2 箇所に持たない）。

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/skills/pipeline-review/scripts/pipeline_flags.py" \
     --deals deals.csv --statuses <ステータス表.json> --format json
   ```
2. **最優先の 1 件を選ぶ**（下の順で最初に当たったもの）。理由には、当たった段と根拠の事実を書く。
3. **推奨アクション 3 つを選ぶ。** 最優先の 1 件を除き、今日・明日が成約予定の未締結 → 準備が済んでいない今日の会議 →
   今週成約予定 → 停滞している案件 → 今週が期限の次アクション、の順で埋める。各アクションに「今やる理由」を 1 行添える。
4. **2 分で読める 1 通にまとめる。** データのあるセクションだけを出す（表は各 5 行まで、超える分は件数だけ）。
5. **届ける。** 会話で頼まれたときは、その場に出して終える。定期実行にするときは通知先を先に確認し、未設定なら有効にしない。
   配信は定期実行の側の仕組みに任せ、担当者ごとに 1 通にする。

## 最優先 1 件の選び方（この順で最初に当たったもの）

1. 確度 90% 以上の案件の会議が今日ある → その会議の準備
2. 今月成約予定で未締結の案件がある → その案件を締結まで進める一手
3. 期限を過ぎた次アクションがある → 最も古いものから
4. 高額の初期案件で 7 日以上動きが無い → 再接触

同じ段に複数あるときは、金額の大きい順、同額なら成約予定の近い順。どれにも当たらなければ、今日の会議のうち金額が最も大きい案件の準備。

## 出力の型（2 分で読める長さ）

```markdown
# 朝のブリーフィング | M 月 D 日（曜日）

## 最優先の 1 件
**[案件名]: [今日やること]**
理由: [当たった段と根拠の事実]

## 今日の数字          ← CRM を参照できたときだけ
| 開いている案件 | 今月成約予定 | 今日の会議 | アクション数 |

## 今日の会議と会議前の一手   ← 予定が分かるときだけ
- [時刻] [会社名]（[種別]）— 状況 1 行。会議前の一手: […]

## 要対応のアラート      ← CRM を参照できたときだけ
| 案件名 | ステータス | 金額 | アラート | 次の一手 |

## 滞留しているフォロー   ← 議事録か次アクションを読めたときだけ
| 相手 | 約束したこと | 滞留日数 |

## 推奨アクション 3 つ
1. **[アクション]** — [今やる理由]
```

## 守ること

- 最優先の 1 件と推奨アクション 3 つは常に出す。**データの無いセクションは作らない**。
  取れなかったことは 1 行で書き、もっともらしい数字で欄を埋めない。
- 停滞の判定は週次レビュー（pipeline-review）と同じ閾値を読む。この Skill で別の閾値を持たない。確度はステータス表の値を使う。
- 読み取りだけ。CRM を更新しない。送信しない。

## フォールバック先

- **CRM を参照できない**: 今日の予定・注力している案件・緊急事項の 3 つを聞いて組み立てる。
- **終業版**（「今日をまとめて」と言われたとき）: 今日完了したこと / ステージが動いた案件 / 明日の予定 / 未完了、の 4 つに切り替える。

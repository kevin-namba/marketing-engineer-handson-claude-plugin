# アウトリーチの文面

アウトリーチ（こちらから連絡する営業）の文面を書く。自動化できるのは文面を書くところまでで、送るかどうかは人が判断する。
入り方は 2 つあり、文面の構成と守ることは共通にする。

| 入り方 | 入力 | 根拠になる事実が無い相手 | 読む節 |
|---|---|---|---|
| 1 社を対話しながら書く | `company-brief` のレポート | **書かない** | 「1 社を書く」 |
| リストから一括で生成する | 1 行 1 社の表・CSV | 汎用の書き出しにして、要レビューの印を立てる | 「リストから一括で生成する」 |

## 前提（共通）

- **調べ方はここに持たない。** 相手について書いてよいのは、企業調査の結果か、その行の入力に実際に書かれている事実だけ。
- **承認済みの実績リスト**（外に出してよい事例・数値・社名）。無ければ利用者に貼ってもらう。貼られなければ実績の段落は書かない。
- **送り手の情報**（会社名・担当者名・価値の提案 1 文・署名・既定の CTA）。初回に確認し、以後は同じものを使う。
- 除外リストに載っている相手、過去の接点が「お断り」の相手には書かない。

## 文面の構成（共通）

パーソナルな書き出し（事実 1 つ）→ 課題の仮説 1〜2 文（断定しない）→ 近い業種の実績 1 件（承認済みリストから）→
心理的ハードルの低い依頼 1 つ。

- 結論・フックから入る。「お世話になっております」で始めない。名乗りは 1 文。段落は 2〜3 文まで。
- フォームは 400 字前後、メールも 1 画面で読める長さ。
- メールの末尾には、送信者の名称・住所・受信拒否の連絡先を表示する。
- 区分（コールド / ウォーム / 再接触 / イベント後）ごとの型と文例は `references/templates.md`（文例の SSOT はここだけ）。

## 1 社を書く

1. **依頼を読む。** 会社・人物・役職・URL、経路（フォームかメールか）、区分。経路が分からなければ 1 回だけ確認する。
2. **企業調査の結果を受け取る。** `company-brief` のレポート（フック候補と出典 URL）か、まとめ調査の 1 行（recent_fact と出典 URL）。
   無ければ先に `company-brief` を回す。
3. **フック候補から 1 つ選ぶ。** 優先順は トリガーイベント（出店・受賞・採用）> 共通のつながり > 相手の公開コンテンツ >
   会社の取り組み > 役職から推測される課題。出典 URL の無い候補は選ばない。
   選べる候補が無ければ書かずに「根拠になる事実が見つかっていない」と返す（汎用の文面を作る工程は無い）。
4. **構成で書く**（上の「文面の構成」）。
5. **件名 3 案とフォロー 3 通を書く。**

   | 通 | 時期 | 中身 |
   |---|---|---|
   | 1 | 3 日後 | 新しい切り口（初回と別の事実か、別の角度） |
   | 2 | 7 日後 | 別の価値（別の実績・役立つ資料。実在するものだけ） |
   | 3 | 14 日後 | 最後の 1 通。役立つものを 1 つ残して終える。圧をかける書き方をしない |

   返信があったら（内容に関係なく）以後のフォローは送らない。この注意を出力の末尾に必ず添える。

```markdown
# アウトリーチ下書き: （相手）
作成日: YYYY-MM-DD / 経路: フォーム | メール / 区分: コールド | ウォーム | 再接触 | イベント後

## 根拠
- 相手: （会社・人物・役職）/ 選んだフック: （種類）— （事実）/ 出典 URL: （URL・取得日）

## 本文（プレーンテキスト）
## 件名 3 案（メールのとき）
## 理由
| 要素（書き出し / フック / 実績 / 依頼） | なぜ選んだか |
|---|---|

## フォロー 3 通
- 3 日後: … / 7 日後: … / 14 日後: …

## 送る前に人が確認すること
- 除外リストに載っていないか / 返信が来ていないか（フォローのとき）
- フォームに「営業目的の投稿はお断り」、アドレスに「営業目的の送信お断り」の表示が無いか
- 書き出しの事実が出典のとおりか
```

## リストから一括で生成する

見込み客のリスト（1 行 1 社）を入力に、1 行 1 社の文面と検査用のメタ列を表・CSV で返す。
量産は 上流（調査でリサーチメモを埋める）→ この節（文面を書く）→ 下流（人が許可して送信）の 3 段で、ここでは調べない。

入力の列は 会社名 / 業種 / 経路 / 区分 / 宛先 / 過去の接点 / リサーチメモ / 出典 URL。列の名前と必須・任意は `references/io-schema.md`。

0. **（メールの行があるとき）アドレスを検証する。** 形式 → MX レコード → ラベルの順。相手には何も送信されない。

   ```bash
   python3 ${CLAUDE_PLUGIN_ROOT}/skills/outreach-draft/scripts/check_addresses.py \
     --in leads.csv --column email --out leads_checked.csv
   ```

   `address_status` が無効の行は書かない。不明の行は要レビューの印を立てる。DNS を引けない環境では `--no-dns` で形式とラベルだけ検査し、
   検証していないことを出力の冒頭に書く。
1. **1 行 1 社の入力を読む。** 必須の列（会社名・経路）が欠けた行は生成せず、備考に理由を書く。
2. **リサーチメモに、書き出しの根拠に使える事実が書かれているかを確かめる。**

   | メモの状態 | 扱い | 確信度 |
   |---|---|---|
   | 相手に固有の事実があり、出典 URL もある | その事実から書き出しを書く | 高 |
   | 事実はあるが出典 URL が無い、または古い | その事実から書くが、要レビューの印を立てる | 中 |
   | 空・業種の一般論だけ | 汎用の書き出しにして要レビューの印を立てる | 低 |

   半分以上が「低」になるときは、生成を進める前に利用者へ伝え、上流（`company-brief` のまとめ調査）に戻すかを確認する。
3. **構成で書く**（上の「文面の構成」）。汎用の書き出しは、相手の業種に共通する状況から入り、
   相手に固有の事実があるかのような書き方をしない。
4. **実績を承認済みのリストと照合する。** リストに無い数値や固有名は差し戻す。合う実績が無い行は実績の段落を省き、備考に「合う実績なし」と書く。
5. **1 行 1 社で出力する**（根拠にした入力列・確信度・要レビューの印・備考を添える）。要レビューの行を先頭に寄せる。
   行数が多いときはサブエージェントに分けてよい（同時に 3〜4 体まで）。出力した CSV は同梱のスクリプトで検査する。

   ```bash
   python3 ${CLAUDE_PLUGIN_ROOT}/skills/outreach-draft/scripts/validate_output.py --in outreach.csv
   ```

   検査するのは、必須の列・本文の記法・汎用の行に要レビューの印があるか・フォームの行に件名が入っていないか・同じ本文の重複。
   `--approved <実績リスト.txt>` を渡すと `evidence_case` も照合する。
6. **捏造の検査（人に渡す前）。** 本文の具体的な言及が、その行の `research_notes` に実在するかを確かめる。無い言及があれば差し戻す。

```plain text
company_name, channel, subject, subject_alt1, subject_alt2, body,
opening_hook, evidence_case, cta,
personalization_source,   # フックの根拠にした入力列。汎用なら generic
confidence,               # 高 / 中 / 低
needs_review,             # true なら人のレビュー必須
notes                     # 不足データ・要最新確認
```

表の前に要約を付ける: 生成 N 行 / 要レビュー M 行 / 生成しなかった行 K 行（理由）/ アドレスの検証（済み・未実施）/ 送る前に人が行うこと。

メールで送る場合は、営業用の送信ドメインを会社の本体のドメインと分け、SPF・DKIM・DMARC の設定を確かめる。

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/skills/outreach-draft/scripts/check_sending_domain.py \
  --domain example-info.com --dkim-selector selector1
```

## 守ること

- 書き出しの事実は 1 つ。出典や入力に書かれていないことを足さない。
- 実績は**承認済みのリストからだけ**引く。相手の業種に近い 1 件だけを選び、盛らない。出典の怪しい業界の数字を使わない。
- 定型の挨拶・機能の羅列・偽のパーソナライズ（「貴社にお勤めとのことで」）を使わない。
- 本文はプレーンテキスト。太字や見出しの記法を使わない。理由や推論は本文に書かず、理由の表か備考の列に入れる。
- 送信しない。文面と、根拠にした事実の出典 URL を返すところまで。送信の直前に除外リストをもう一度引き、
  「営業目的の送信お断り」の表示がある相手には送らない。返信があった相手には、内容に関係なく次の 1 通を送らない。

## フォールバック先

- **（1 社）企業調査の結果が無く、調査も回せない**: 利用者に相手の事実（URL 付き）を 1 つ貼ってもらう。貼られなければ書かない。
- **（一括）リサーチメモが全行で空**: 生成せず、`company-brief` のまとめ調査に戻すことを提案する。利用者が汎用でよいと言えば、全行を汎用＋要レビューで出す。
- **承認済みの実績リストが無い・近い業種の実績が無い**: 実績の段落を省き、「実績は未記載」と理由の表か備考に書く。
- **経路が決まらない**: フォーム用（短い）とメール用（件名つき）の両方を出し、どちらを使うかは人が決める。
- **CSV を書き出せない**: 表として会話に出す。本文の改行は保つ。

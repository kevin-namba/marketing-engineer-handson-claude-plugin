# 営業文面の一括生成

見込み客のリスト（1 行 1 社）を入力に、1 行 1 社の文面と検査用のメタ列を表・CSV で返す。
量産は 上流（調査でリサーチメモを埋める）→ エンジン（この Skill）→ 下流（人が許可して送信）の 3 段で、エンジンには調べさせない。

## 入力（1 行 1 社）

会社名 / 業種 / 経路 / 区分 / 宛先 / 過去の接点 / リサーチメモ / 出典 URL。列の名前と必須・任意は `references/io-schema.md`。
あわせて、**承認済みの実績リスト**（外に出してよい事例・数値・社名）と**送り手の情報**（会社名・担当者名・署名・既定の CTA）を受け取る。
無ければ利用者に貼ってもらう。

## 手順

0. **（メールの行があるとき）アドレスを検証する。** 形式 → MX レコード → ラベルの順。相手には何も送信されない。

   ```bash
   python3 ${CLAUDE_PLUGIN_ROOT}/skills/outreach-copy/scripts/check_addresses.py \
     --in leads.csv --column email --out leads_checked.csv
   ```

   `address_status` が無効の行は書かない。不明の行は要レビューの印を立てる。DNS を引けない環境では `--no-dns` で形式とラベルだけ検査し、
   検証していないことを出力の冒頭に書く。
1. **1 行 1 社の入力を読む**（この Skill は調べない）。必須の列（会社名・経路）が欠けた行は生成せず、備考に理由を書く。
   過去の接点が「お断り」の行、除外リストに載っている行は生成しない。
2. **リサーチメモに、書き出しの根拠に使える事実が書かれているかを確かめる。**

   | メモの状態 | 扱い | 確信度 |
   |---|---|---|
   | 相手に固有の事実があり、出典 URL もある | その事実から書き出しを書く | 高 |
   | 事実はあるが出典 URL が無い、または古い | その事実から書くが、要レビューの印を立てる | 中 |
   | 空・業種の一般論だけ | 汎用の書き出しにして要レビューの印を立てる | 低 |

   半分以上が「低」になるときは、生成を進める前に利用者へ伝え、上流（`company-brief` のまとめ調査）に戻すかを確認する。
3. **書き出しを書く。** 構成は 書き出し → 課題の仮説 1〜2 文（断定しない）→ 実績 1 件 → 依頼 1 つ。段落は 2〜3 文まで。
   区分（cold / warm / event / re-engage）ごとの型と文例の SSOT は `../outreach-draft/references/templates.md`（この Skill には写さない）。
   汎用の書き出しは、相手の業種に共通する状況から入り、相手に固有の事実があるかのような書き方をしない。
4. **実績を承認済みのリストと照合する。** リストに無い数値や固有名は差し戻す。合う実績が無い行は実績の段落を省き、備考に「合う実績なし」と書く。
5. **1 行 1 社で出力する**（根拠にした入力列・確信度・要レビューの印・備考を添える）。要レビューの行を先頭に寄せる。
   行数が多いときはサブエージェントに分けてよい（同時に 3〜4 体まで）。出力した CSV は同梱のスクリプトで検査する。

   ```bash
   python3 ${CLAUDE_PLUGIN_ROOT}/skills/outreach-copy/scripts/validate_output.py --in outreach.csv
   ```

   検査するのは、必須の列・本文の記法・汎用の行に要レビューの印があるか・フォームの行に件名が入っていないか・同じ本文の重複。
   `--approved <実績リスト.txt>` を渡すと `evidence_case` も照合する。
6. **捏造の検査（人に渡す前）。** 本文の具体的な言及が、その行の `research_notes` に実在するかを確かめる。無い言及があれば差し戻す。

## 出力（1 行 1 社）

```plain text
company_name, channel, subject, subject_alt1, subject_alt2, body,
opening_hook, evidence_case, cta,
personalization_source,   # フックの根拠にした入力列。汎用なら generic
confidence,               # 高 / 中 / 低
needs_review,             # true なら人のレビュー必須
notes                     # 不足データ・要最新確認
```

表の前に要約を付ける: 生成 N 行 / 要レビュー M 行 / 生成しなかった行 K 行（理由）/ アドレスの検証（済み・未実施）/ 送る前に人が行うこと。

## 守ること

- 調べない。相手について書いてよいのは、その行の入力に実際に書かれている事実だけ。
- 実績は**承認済みのリストからだけ**引く。相手の業種に近い 1 件だけを選び、盛らない。
- 本文はプレーンテキスト。太字や見出しの記法を使わない。理由や推論は本文に書かず、備考の列に入れる。
- 偶然を装ったパーソナライズ（「貴社にお勤めとのことで」）を使わない。
- 送信しない。送信の直前に除外リストをもう一度引き、「営業目的の送信お断り」の表示がある相手には送らない。
  返信があった相手には、内容に関係なく次の 1 通を送らない。

メールで送る場合は、営業用の送信ドメインを会社の本体のドメインと分け、SPF・DKIM・DMARC の設定を確かめる。

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/skills/outreach-copy/scripts/check_sending_domain.py \
  --domain example-info.com --dkim-selector selector1
```

## フォールバック先

- **リサーチメモが全行で空**: 生成せず、`company-brief` のまとめ調査に戻すことを提案する。利用者が汎用でよいと言えば、全行を汎用＋要レビューで出す。
- **承認済みの実績リストが無い**: 実績の段落を省いて生成し、全行の備考に「実績は未記載」と書く。
- **CSV を書き出せない**: 表として会話に出す。本文の改行は保つ。

# パイプラインレビューと売上予測

パイプライン（進行中の商談の一覧）を、同じ案件表と同じステータス表から 2 通りに見る。
どちらも計算と判定はスクリプトが決定的に行い、生成 AI は説明文だけを書く。

| 頼まれたこと | 読む節 | 出すもの |
|---|---|---|
| 週次のレビュー（停滞・棚卸し） | 「週次のレビュー」 | 今週注力する 5 件、フラグ別の一覧、削除候補、データの欠け、更新案 |
| 売上の見込み（フォーキャスト） | 「売上予測」 | 3 シナリオ、ギャップ、コミットとアップサイド、ギャップの埋め方 |

## 入力（共通）

- **商談一覧**: CRM の MCP ツールで開いている商談（締結・失注・保留は除く）を読み取り専用で取得する。取得できなければ CSV か
  1 行 1 案件の貼り付け（CSV に直す）。どの経路で取ったかを出力の先頭に書く。
  読む項目: 案件名 / ステータス / 金額（月額）/ 契約期間（月数。単発は 1。売上予測で使う）/ 成約予定（獲得目標月）/ 担当者 /
  次アクション / チャネル / 最終更新日 / ステータス変更日 / 相手側の連絡先の数 / 先送り回数 / 最終反応日 /
  コミット（人が付けた yes / no。任意。売上予測で使う）。列の見出しと、列が無いときの扱いは `references/deal-columns.md`。
- **ステータス表**（確度と「開いているか」の SSOT。自社の設定 1 箇所）: 場所が分からなければ 1 回だけ聞く。まだ無ければ
  `references/statuses.example.json` を見本に自社の値で作ってもらう（見本の確度は一例）。

## 週次のレビュー

週に 1 回、同じ基準で見直す。判定を毎週同じにすることがこの節の価値。
4 つの観点: ステージの進み具合 / 活動の新しさ / 期日の正確さ / 連絡先の数。

閾値の SSOT は `references/thresholds.json`（依頼で上書きできるが、実行のたびに変えない）。
自社用に変えるときはこのファイルを写して直し、以後は毎回その写しを読む。

| フラグ | 条件 | 推奨する対処 |
|---|---|---|
| 停滞 | 最終更新から 14 日以上 | 再接触、またはステータスを下げる |
| 行き詰まり | 同じステータスに 30 日以上 | 推進策を決める、相手側の窓口を増やす、失注処理 |
| 期日超過 | 成約予定が今月より前 | 期日を更新する、翌期へ繰り越す、失注 |
| 単線 | 相手側の連絡先が 1 人 | 別の利害関係者を特定する |
| 衛生 | 次アクション・期日・金額・担当者・チャネルのいずれかが空 | 埋める（埋まらない案件は予測から外す） |
| 削除候補 | 60 日以上反応なし、または 3 回以上の先送り | 失注として処理するかを人が決める |

1. **閾値で機械的にフラグを付ける**（判定に生成 AI を使わない）。一覧を CSV にして、同梱のスクリプトで判定する。

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/skills/pipeline-review/scripts/pipeline_flags.py" \
     --deals deals.csv --statuses <ステータス表.json> --format json
   ```

   `--thresholds` で自社の閾値ファイル（省略時は同梱の既定値）、`--today YYYY-MM-DD` で基準日を指定できる。
   スクリプトを実行できない環境では、上の表の条件を 1 件ずつ当てはめる（閾値の数字は変えない）。
2. **優先順位を並べる。** 重みは 成約の近さ 30 / 規模 25 / ステージ 20 / 活動 15 / リスク 10（スクリプトが換算して合計する）。
   重みを変える指示があれば `weights` を直して再計算し、どの重みで並べたかを出力に書く。
3. **形状を集計する。** ステージ別・成約月別・規模別の件数と金額。金額が空の案件は合計に入れず、件数を別に書く。
4. **推奨アクションと更新案を出す。** 今週注力する 5 件に理由 1 行と次の一手を書く。CRM で変えたほうがよい項目は「更新案」の表にする。

```markdown
# パイプラインレビュー（基準日 YYYY-MM-DD）
データの取得経路: CRM の MCP ツール / CSV / 貼り付け　対象: 開いている商談 N 件（除外 M 件）
閾値: 停滞 14 日 / 行き詰まり 30 日 / 単線 1 人 / 削除候補 60 日・3 回

## 今週注力する 5 件
1. [案件名] — 理由 1 行。次の一手: […]
## フラグ別の一覧
| 案件名 | ステータス | 滞留日数 | フラグ | 推奨する対処 |
## 削除候補
| 案件名 | 金額 | 理由（N 日反応なし / N 回先送り） |
## データの欠け
| 空欄の項目 | 件数 | 案件 |
## パイプラインの形状
ステージ別 / 成約月別 / 規模別（件数・金額）
## 更新案（CRM は変更していない）
| 案件名 | 項目 | 現在の値 | 変更案 | 根拠 |
```

## 売上予測（加重フォーキャスト）

フォーキャスト（売上予測）を、確度 × 単価 × 期間の加重和で出す。
依頼した人に聞くもの: 対象の期間 / 期間の売上目標 / 期間内にすでに締結した額。目標が無ければギャップとカバレッジは「未設定」。

| 値 | 式 |
|---|---|
| 案件価値 | 月額 × 契約期間 |
| 加重値 | 案件価値 × ステータス表の確度 |
| ベスト | 締結済み + 対象の開いている案件の全件 |
| 想定 | 締結済み + 加重値の合計 |
| ワースト | 締結済み + コミット案件だけ |
| ギャップ | 目標 − 想定 |
| カバレッジ | 対象の開いている案件の合計 ÷ 目標（目安 3 倍。2 倍未満は警告） |

対象は、成約予定が期間の中にある開いている案件。

1. **失注・保留を除き、ステータス表の確度をそのまま使って計算する。**

   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/skills/pipeline-review/scripts/weighted_forecast.py" \
     --deals deals.csv --statuses <ステータス表.json> \
     --period 2026-10:2026-12 --target 6000000 --closed 1200000 \
     --save-dir <作業フォルダの外の保存先>
   ```

   スクリプトを実行できない環境では、上の式を表にして 1 件ずつ計算し、途中の値（案件価値・加重値）を出力に残す。
2. **3 シナリオを出す。** 前提を 1 行ずつ添える。
3. **コミットとアップサイドに分ける。** スクリプトは、コミットの列が空の案件を「確度が下限（既定 90%。`--commit-min`）以上」で仮に分ける。
   仮の区分を利用者に見せて確認し、変更があれば CSV のコミット列に書いて再計算する。コミットには理由、アップサイドにはリスク要因を 1 行ずつ書く。
4. **ギャップの埋め方を出す。** 加速（前倒しできる案件）/ 再活性化（止まっているが金額の大きい案件）/
   新規パイプライン（目安のカバレッジに届くために必要な金額）の 3 つを、案件名と金額を入れて書く。
5. **今回の予測を日付付きで保存する。** `--save-dir` が書き出した `forecast-YYYY-MM-DD.json` を、作業の環境の外に残す（保存先は利用者に確認する）。
   前回の予測があれば `--previous <前回の JSON> --actual <その期間の実績>` で比べる。実績が分からなければ精度は「未計測」。

```markdown
# 売上フォーキャスト: [期間]（計算日 YYYY-MM-DD）
データの取得経路: […]　確度の出どころ: [ステータス表の場所]

## サマリー
| 目標 | 締結済み | 開いている案件 | 加重 | ギャップ | カバレッジ |
## 3 シナリオと前提
| シナリオ | 金額 | 目標比 | 前提 |
## ステージ別
| ステータス | 件数 | 合計 | 確度 | 加重 |
## コミット（理由）／アップサイド（リスク）
| 案件名 | 金額 | ステータス | 成約予定 | 理由・リスク要因 |
## ギャップの埋め方
1. 加速 / 2. 再活性化 / 3. 新規パイプライン
## 予測から外した案件
| 理由（金額か期間が空 / 成約予定を過ぎている / ステータスが表に無い） | 件数 | 案件 |
## 前回予測との差
```

## 守ること

- 金額・日付・期間が空の案件を推測で埋めない。レビューでは空のまま「データの欠け」に出し、売上予測からは外して件数と案件名を出力に書く。
- 判定に必要な列が無いフラグは「該当なし」ではなく「未取得」と書き、どの列があれば判定できるかを添える。
- 成約予定は「署名を期待する日」であって「願う日」ではない。過ぎた予定は更新か翌期へ繰り越すか失注の 3 択。
  成約予定を過ぎた案件は売上予測に入れず、レビューの更新案に出す。
- 確度をこの Skill の側で持たない（SSOT を 2 つにしない）。ステータス表に無いステータスの案件は計算に入れず、名前を出力に書く。
- コミットは正直に絞る。確度が高くても、直近の活動が無い案件はアップサイドに置く。
- CRM を変更しない。変えたほうがよいものは更新案として別に並べ、人が反映する。
- 大量に流入した初期段階のリード（展示会後など）は 1 件ずつ扱わず、まとめてフォロー計画を立てる。

## フォールバック先

- **CRM を参照できない**: CSV か貼り付けを受け取って進める。
- **列が足りない**: 判定できるフラグだけを出し、判定できなかったフラグは「未取得」として必要な列を書く。
- **口頭の説明しか無い**: 聞いた内容を表に起こし、足りない項目を 1 回だけ確認する。確認できなかった項目は「未取得」のまま進める。
- **ステータス表が無い**: 売上予測は計算を始めず、見本を示して自社の確度を決めてもらう。
- **保存先に書き込めない**: 予測の JSON をローカルに残し、保存先のパスと手動で移す方法を案内する。
